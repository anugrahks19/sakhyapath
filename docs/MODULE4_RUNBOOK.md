# Module 4 operator runbook and evidence packet

## Run the local prototype

Follow [Module 2 setup](MODULE2_RUNBOOK.md) to install pinned dependencies and the local FastALPR models. Start the backend and frontend as documented there. Sign in with your configured operator key. Imported owned feeds must be explicitly labelled `owned_live` or `owned_replay`; Sentinel URLs and credentials stay on the server.

1. Run an owned-feed end-to-end benchmark on the intended host: `python scripts/benchmark_active_pursuit.py --duration 20 --record-local-db`. It opens one H.264 and one H.265 RTSP replay at 960×540, warms the model, then measures decoded and analyzed frame deltas. On Windows with the local CUDA installation used during development, set `SAKHYAPATH_CUDA_DLL_DIR` to the Torch DLL directory before running. The output is [the capacity evidence](../output/benchmarks/module4_owned_pipeline.json). `--record-local-db` saves the measured row into the local prototype DB. Rebenchmark after changing hardware, model, codec, resolution, or feed mix.
2. Build an Evidence Journey for a plate already observed on an owned feed. Its Module 4 section shows the latest supported confirmed sighting and camera ranking. A candidate reading does not become a pursuit driver.
3. Click **Start measured pursuit**. The scheduler chooses at most four cameras, keeps a baseline across the selected set, distributes spare fps by rank, and lists excluded cameras. Compare requested and currently acknowledged rates. New confirmed evidence or material feed-health changes make a new revision; sustained model latency overload triggers a lower-rate revision.
4. Refresh the coverage ledger after a few seconds. Inspect `planned_frames`, `received_frames`, `analyzed_frames`, `decode_errors`, health and result code. Bring one owned feed down; its window must not become a negative vehicle finding. Export the journey PDF and compare its schedule and ledger to the API response.
5. Stop pursuit sampling. Old windows remain in the database with final counter snapshots.

The capacity measurement API is `POST /api/v1/capacity/measurements` for an operator, using `duration_seconds`, `feed_count`, `decoded_frames`, `analyzed_frames`, `codec`, `resolution`, `model_provider`, `source_mode`, `method` and `evidence_note`. It rejects inconsistent counts and durations under 10 seconds. Its row is an operator-supplied measurement; review the linked benchmark evidence before trusting it. Read `GET /api/v1/capacity/measurement` and operator `GET /api/v1/metrics` for current state.

Pursuit endpoints are `GET /api/v1/pursuits/{id}/rankings`, `POST/GET/DELETE /api/v1/pursuits/{id}/schedule`, and `GET /api/v1/pursuits/{id}/coverage`. The internal worker acknowledgement is based on real analyzed frames and exposed in the schedule; a browser cannot assert an applied rate. All endpoints enforce the existing session and department checks. Starting/stopping a schedule requires the operator role in this prototype.

## Verification evidence

- Automated integration: `python -m pytest -q tests/test_active_pursuit.py`. The deterministic fixture checks an absent benchmark, rank determinism, a confirmed driver, a candidate that does not drive, an applied-rate acknowledgement, all four ledger results, a changed schedule, and PDF parity.
- Whole build: `python -m pytest -q`; `npm run build --prefix frontend`.
- PDF layout QA: `python scripts/create_module4_demo.py` creates [a clearly labelled synthetic report](../output/pdf/module4_synthetic_layout_qa.pdf) containing all four coverage codes. It is for pagination review only; the API report in the integration test uses persisted pursuit data. The rendered pages were inspected for section flow, text legibility, and page footer placement.
- Fair controlled-frame comparison: `python scripts/compare_pursuit_sampling.py`. [The JSON record](../output/benchmarks/module4_equal_budget_comparison.json) runs uniform and adaptive samplers from reset on identical annotated visibility windows with the same 3 fps total frame budget, below the measured local limit. It reports both a schedule-only oracle and actual FastALPR reads of the official sample/blank frames. One route favours adaptive sampling and one surprise route favours uniform sampling; it is not a live multi-camera or Indian-road improvement claim.
- Benchmark provenance: the owned replay uses the official FastALPR sample image and local MediaMTX publishers. The 20.634-second mixed H.264/H.265, 960×540 run decoded 498 frames and analyzed 249 across two feeds: 12.067 fps observed, with an 8.447 fps scheduler ceiling after 30% reserve. CUDA inference was reported; sampled model latency p95 was 76.45 ms, peak GPU utilization reached 100%, peak backend process RAM was 1007.1 MiB, and the relay recorded 5,302,451 bytes in each direction. These are local decode/inference and relay-path observations with publisher encoding sharing the host. They do not measure Indian plate accuracy or statewide capacity. A Government load test is pending authorized access.

## Demo and submission sequence

Show the registry and camera map first, then a decoded owned RTSP/HLS frame with source PTS and health. Show a real model sighting, evidence hash, watchlist alert, and registration search. Open the journey, distinguish supported observations from inferred links, and download the PDF. Start Active Pursuit from a supported confirmed sighting and show a changed applied rate. Disconnect one owned feed and show `feed unavailable`; show an undersampled/excluded camera as `insufficient coverage`. Disclose the measured laptop feed counts and fps, the equal-budget comparison's mixed result, and the unverified Government feed and clock gates. Record a Sentinel demo only after obtaining legitimate sandbox access from the event organizer and verifying the permitted base URL, credentials, and network path.
